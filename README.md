# 플랜두씨 다이어리

계획(Plan) → 실제로 한 일(Do) → 돌아보기(See)를 하나로 잇는 다이어리입니다.

> 과제 7부터 가입·로그인이 붙었습니다. 로그인하지 않으면 모든 화면이 로그인 화면으로 가고, 자료는 주인(로그인한 사람)의 것만 보입니다.

## 카드 1 — 계획과 수정 이력

| 표 | 하는 일 |
|---|---|
| `plans` | 계획의 지금 값. `id`는 처음 만들 때 정해지고 바뀌지 않습니다. |
| `plan_revisions` | 계획의 모든 버전. `version 1`이 처음 세운 계획입니다. 쌓기만 하고 고치거나 지울 수 없습니다. |

계획 항목: 이름 · 분야 · 기간(시작/끝) · 우선순위(높음/보통/낮음) · 성공 기준 · 예상 시간(분, 하루 기준 또는 기간 전체 기준).

이력은 앱 코드가 아니라 DB 트리거가 남깁니다 (`db/001_plans.sql`).
계획을 만들거나 고치면 그 순간의 내용이 `plan_revisions`에 한 줄 추가되고, 고칠 때는 `version`만 1 오릅니다.
그래서 SQL로 직접 고쳐도 이력이 빠지지 않습니다.

## 카드 2 — 할 일

| 표 | 하는 일 |
|---|---|
| `tasks` | 계획에 딸린 할 일. `plan_id`로 계획 하나를 가리킵니다. |

할 일 항목: 이름 · 메모 · 마감일 · 우선순위 · 태그(여러 개) · 예상 시간(분) · 상태(진행 중/완료, 완료한 시각).
`/tasks`에서 만들고, 완료로 바꾸고 되돌리고, `/tasks/번호`에서 고치고 지웁니다.

검색·거르기·정렬은 모두 서버의 SQL에서 처리하고, 조건은 주소(`?q=&plan=&status=&priority=&tag=&due=&sort=`)에 남습니다.
정렬은 값이 같을 때를 위해 마지막에 항상 할 일 번호를 둬서, 같은 조건이면 언제 열어도 같은 순서입니다.

| 정렬 | 순서 |
|---|---|
| 마감일 빠른 순 (기본) | 마감일 ↑ (없으면 맨 뒤) → 우선순위 높은 순 → 번호 ↑ |
| 우선순위 높은 순 | 우선순위 → 마감일 ↑ (없으면 뒤) → 번호 ↑ |
| 예상 시간 긴 순 | 예상 시간 ↓ → 마감일 ↑ (없으면 뒤) → 번호 ↑ |
| 최근 만든 순 | 만든 시각 ↓ → 번호 ↓ |

## 카드 3 — 실제로 한 일

| 표 | 하는 일 |
|---|---|
| `task_logs` | 실행 기록. 시작 시각 · 끝난 시각 · 실제로 걸린 시간(분) · 막혔던 이유. `task_id`로 할 일 하나에 붙습니다. 고칠 수 없고 쌓기만 합니다. |
| `task_completions` | 완료 기록. 돌아보기(`/review`)의 완료 수는 여기서 셉니다. 되돌리면 지우지 않고 `reopened_at`만 적습니다. |

실행 기록은 할 일·계획과 다른 표라서 저장해도 원래 계획 값(예상 시간·마감일 등)은 바뀌지 않습니다.
`/tasks/번호`에서 계획 값과 실제 합계를 나란히 보여 줍니다.

완료가 두 번 쌓이지 않게 데이터베이스가 막습니다 (버튼 잠금에 기대지 않음).
- 완료 폼마다 새 요청 키(`request_key`, unique)를 넣어, 연달아 눌러 같은 요청이 두 번 와도 한 건만 들어갑니다.
- 할 일마다 되돌리지 않은 완료는 하나만 있을 수 있습니다 (부분 unique 인덱스). 다른 탭에서 눌러 키가 달라도 막힙니다.
- 완료 기록을 넣는 것과 할 일을 '완료'로 바꾸는 것은 한 SQL 문이라 함께 되거나 함께 안 됩니다.

## 카드 4 — 돌아보기, 그리고 다음 계획으로

- `/review` : 기간(전체·오늘·이번 주·지난주·이번 달·직접)별, 계획별 집계. 기간 안의 할 일 = 마감일이 그 기간 안인 할 일(마감일이 없으면 만든 날, 서울 기준).
  - 계획 수 = 그 계획의 지우지 않은 할 일 수 · 완료 수 = 그중 지금 완료 상태 · 지연 수 = 완료 안 됐고 마감일 < 서울 오늘
  - 막힘 수 = 실행 기록에 막힌 이유가 하나라도 있는 할 일 수 · 예상 = 예상 시간 합 · 실제 = 실행 기록 합 · 차이 = 실제 − 예상 (모두 분, 없으면 0)
- 숫자를 누르면 `/review/[metric]` 근거 기록으로 간다. 그 숫자를 만든 할 일·실행 기록(막힌 이유, 완료 기록 번호 포함)과 다시 더한 합계가 나온다. 조건은 `lib/review.js`의 `METRICS` 한곳에서 집계와 근거가 같이 쓴다.
- 고칠 점 한 줄(`review_notes`, db/004_reviews.sql) : 돌아보기에서 정해 기존 계획이나 새 계획으로 넘긴다. 정할 때의 숫자를 함께 저장하고, 넘긴 계획 화면 위쪽 "돌아보기에서 넘어온 고칠 점"에 보인다. 지우거나 바꿀 수 없다.

## 과제 7 카드 1 — 가입·로그인·로그아웃

| 무엇 | 어디 |
|---|---|
| 인증 서비스 | Supabase Auth, `@supabase/ssr` 0.12.7 + `@supabase/supabase-js` 2.118.0 |
| 로그인 안 했으면 막기 | `middleware.js` (화면은 `/login`으로, `/api/*`는 401) + 모든 화면·Server Action 첫 줄 `requireUser()` (`lib/auth.js`) |
| 로그인 확인 방법 | `supabase.auth.getUser()` — 쿠키의 토큰을 믿지 않고 매번 Supabase Auth 서버에 묻는다. 로그아웃으로 지운 세션의 쿠키는 거절된다 |
| 가입·로그인·로그아웃 | `app/signup`, `app/login`, `app/auth-actions.js`, 머리의 로그아웃 버튼 |
| 주인 칸 | `db/005_owner.sql`: 6개 표 모두 `user_id`(not null). 할 일·기록·고칠 점은 같은 주인의 계획·할 일에만 붙도록 (id, user_id) 외래 키 |
| 내 자료만 | `lib/*.js`의 모든 SQL에 `user_id = 로그인한 사람` 조건 |
| 과제 6 자료 옮기기 | 계획이 없는 계정의 첫 화면 "과제 6 자료 가져오기" (`lib/import.js`). 과제 6의 `/api/export` 파일을 한 트랜잭션으로 넣는다 |

## 실행

```bash
cp .env.example .env.local   # DATABASE_URL, NEXT_PUBLIC_SUPABASE_URL/ANON_KEY 채우기
npm install
npm run dev
```

표가 없으면 첫 요청 때 `db/` 아래 SQL을 이름 순서대로 한 번 적용합니다. 직접 적용하려면 `npm run db:migrate`.

## 배포 (Vercel + Supabase)

1. Vercel에서 이 저장소를 Import 합니다.
2. Vercel 프로젝트 > Storage 에서 Supabase를 연결하거나, Supabase 프로젝트의
   Connection string(Transaction pooler, 6543)을 `DATABASE_URL` 환경 변수로 넣습니다.
3. 다시 배포합니다.

`DATABASE_URL`은 서버에서만 씁니다. 브라우저로 내려가지 않고, 모든 표에는 RLS를 켜 두어 Supabase 공개 키로는 읽거나 쓸 수 없습니다.
